# 云函数通道（真机可用）

## 为什么需要它

真机（预览版/体验版/正式版）会校验 **request 合法域名**，而 `*.supabase.co` 属境外域名，
**无法完成 ICP 备案** → 配不进白名单 → 真机请求必然失败：

```
request:fail url not in domain list:gzpuxgkpblpbpdpfvpof.supabase.co
```

表现：推荐页显示 `⚠️ 推荐数据拉取失败,显示缓存` + **前一天的缓存数据**；组串保存同样失败（同一个域名）。
开发者工具里勾「不校验合法域名」只对模拟器生效；手机端必须「打开调试」才行（每次都要点）。

**根治**：小程序 → 云函数 `bear_api` → Supabase。云函数在腾讯云国内机房**出网**，
不受小程序侧域名白名单限制，手机不用开调试。

```
小程序 wx.cloud.callFunction({name:'bear_api', data:{fn, args}})
   → 云函数 index.js → core.js.callSupabaseRpc()
   → https://<proj>.supabase.co/rest/v1/rpc/<fn>  (带 MINI_TOKEN + anon key)
   → { ok:true, data } / { ok:false, error }
```

## 一次性开通（微信开发者工具，人工 1 分钟）

1. 打开小程序项目 → 顶部工具栏点 **「云开发」** → **开通**（个人主体可用，有免费额度）
2. **创建环境**（名字随意，如 `bear-prod`）→ 复制 **环境 ID**（形如 `bear-prod-1g0abc12de3456`）
3. 填进 `miniprogram/utils/config.js` 的 `CLOUD_ENV`


## 密钥放哪

优先级：**云函数环境变量** `SUPABASE_URL` / `SUPABASE_ANON_KEY` / `MINI_TOKEN`
（云开发控制台 → 云函数 → bear_api → 配置 → 环境变量）> 同目录 `config.js`。

ESPN 中转另有两个可选项，同一条优先级链：`ESPN_RELAY`（形如 `http://<节点IP>:8899`）与
`ESPN_RELAY_TOKEN`；**不配则自动退回直连 `site.web.api.espn.com`**（功能不变，只是慢）。

`config.js` 已 gitignore；虽不入库，但**会随函数包上传到微信云**，属可接受（仅自己可见）。
节点上的那份副本在 `/opt/espn-relay/env`（600, root）—— **全库只有这两处**，任何文档/提交里都不出现。

## 比分从哪来（2026-09-15 实测定稿）

**结论：真机比分走云函数，实时比分可用**（前提：云函数已部署 + 小程序 `config.js` 开 `ESPN_CLOUD`）。

### 403 是「主机名」问题，不是 IP 段封锁

2026-09-15 先测出云函数出网 403 + Akamai `Access Denied`，当时判成"IP 段封锁"。**这个判断是错的**：
同一台机器、同一份请求头，换主机名就通 —— `site.api.espn.com` 被 ESPN 自家 Akamai WAF 的
主机名规则挡掉，而 **`site.web.api.espn.com` 返回同一份 JSON 是 200**。

| 主机名 | 本机(国内住宅 IP) | 东京 Vultr | 腾讯云云函数 |
|---|---|---|---|
| `site.api.espn.com` | 200 | 403 | 403 |
| `site.web.api.espn.com` | 200 | 200 | **200** |

两主机的返回体结构完全一致（顶层 `{leagues,events,provider}`）。所以云通道本身是通的，
真机 `wx.request` 那条路才是真死（境外域名无法 ICP 备案 → 配不进 request 合法域名）。

**防回退**：主机名两处必须同步 —— 云函数 `core.js` 的 `ESPN_SCOREBOARD_HOST` 与小程序
`espn.js` 的 `boardUrl()`。冒烟 ⑬ 有专门断言卡这条，改回去真机比分就又是"永远空"。

### 那为什么还要中转（东京节点 `espn-relay`）

不是绕过封锁（换主机名已解决），是**躲超时**：云函数超时 **3 秒**，而腾讯云直连 ESPN 跨境单程
实测 1.7~3.3 秒 —— 三次里挂一两次，真机上就是"比分时有时无"。中转把跨境段换成
「腾讯云→东京(约 0.1s) + 东京→ESPN(约 0.5s)」。

中转实现见 `okx-proxy/espn-relay/relay.py`（部署在东京 `108.61.246.121`，systemd 服务
`espn-relay`，监听 8899/tcp）。**只转发 `soccer/<league>/scoreboard` 这一条路径**，
须带 `x-bear-token` 头；地址与令牌只存在于云函数的 `config.js`（已 gitignore），不入库。

### 三次优化，把云函数从"贴着超时线"拉回来

用 `args.perf` 逐段打点（`node tools/_diag_espn.js esp.1 20260915 8 --perf`）测出来的：

| 优化 | 手段 | 实测效果 |
|---|---|---|
| ① 缩包 | 中转侧归一化成 `{rows:[...]}`（40KB → 255B） | 方向对，但**不是瓶颈**（仍偶发 >3s） |
| ② 连接复用 | `core.js` 自建 `keepAlive` agent（Node 16 全局 agent 默认 `keepAlive=false`，每次都重新跨境握手） | 热容器 `建连=0ms` |
| ③ 结果缓存 | 中转侧按 (联赛,日期) 缓存 45 秒（`RELAY_CACHE_TTL`） | 削掉稳定的东京→ESPN 500ms |

效果：函数内出网 **1155~2679ms → 266~646ms**；连打 8 次全部成功（改前三次挂一两次）。

**剩下的不可控项**：腾讯云↔东京那一段本身的抖动（实测 TTFB 145ms~2678ms，同一连接复用下
依然如此），以及云函数 3 秒硬超时。对策两条：

- 小程序 `espn.js` 失败**重试一次**（`ESPN_CLOUD_RETRY`，只对只读取数，写操作绝不重试）；
- 想根治得在**云开发控制台 → 云函数 → bear_api → 配置 → 超时时间**改成 20 秒 ——
  CLI 没有这个参数、本机也没有腾讯云凭据，只能手工点一次（属可选保险，非必须）。

要点（与 Supabase 通道共用的部分）：
- 联赛码只做**形状校验**（`^[a-z][a-z0-9_]*(\.[a-z0-9_]+)*$`，≤32 字符）而非写死清单 ——
  每日场次会引入新联赛码（9-15 就新增 `eng.league_cup`/`afc.champions`/`conmebol.libertadores`），
  写死清单意味着每加一个联赛都要重新部署云函数。
- `espn_scoreboard` 分支**不校验 Supabase 配置**（在 `index.js` 里先于 `assertCfg` 分发），两者互不依赖。
- 小程序侧通道选择收在 `utils/espn.js` 的 `pickChannel()`：注入 fetcher > `ESPN_CLOUD` 云代理 >
  开发者工具直连 > 真机（立即失败）。结算轮询的去重取板器用 `espn.makeBoardFetcher(cache)`，
  **不要在页面里自己包 `defaultFetcher`**，那会绕过这层判断。
- 归一化口径有**跨语言漂移**风险（`relay.py` 的 `normalize()` 与 `core.js` 的 events 分支各写一份）。
  冒烟 ⑮ 用同一份 fixture 交叉核对两边结果必须逐字段一致 —— 改任一边的口径都会立刻红。

## 竞彩赔率实时化（`jc_live`，2026-09-15）

**为什么单开一条：** `data/predictions.js` 里每场的 `sp`/`hhad`/`spHandicap`，以及 `hc7`/`max7`
两个方案块的腿赔率与倍数，都是**每天构建那一刻**从体彩官方抓的快照（`tools/_fetch_jc.js` →
`tools/_build<MMDD>.js`），之后官方一路浮动、页面却停在构建值。9-15 用户拿官方足球计算器的
实拍票一比：8 条腿里站点只有 1 条与官方一致 —— 于是"数据不对"。

**取数源：** `webapi.sporttery.cn/gateway/jc/football/getMatchCalculatorV1.qry?poolCode=<had|hhad>&channel=c`

- ★**一次只回一个彩池**：`poolCode=had` 的返回体里 `hhad` 是空的（反之亦然）。两个都必须打再按
  `matchNumStr` 合并 —— 只想省一次请求会**静默丢掉整个让球盘**，让球 7 关会整块停在旧值。
- 不在返回池里的场次 = 已过销售截止被官方下架 → 标 `oddsClosed`，赔率保留构建值供回顾但**禁投**
  （`makeLeg` 直接返回 null，勾选后下架会被 `switchJcKind` 从票里撤掉）。
- 与 ESPN 那条通道**互不依赖**：这是国内域名，云函数在腾讯云国内机房 → 国内→国内，实测 333ms，
  没有跨境那 3 秒超时的毛病，**故意不做结果缓存**（缓存会把要修的"陈旧"又请回来）。

### 两条独立通道

| | 小程序 | 网站 |
|---|---|---|
| 代码 | `miniprogram/utils/jc.js` | `assets/live-odds.js`（浏览器 IIFE，暴露 `window.LiveOdds`） |
| 取数 | 云函数 `bear_api` 的 `jc_live` 分支 | **浏览器直连**官方 API |
| 为什么能直连 | — | 官方响应头带 `Access-Control-Allow-Origin: *` → 跨域可读，网站不需要云函数/中转/服务器 |
| 入口 | `pages/index/index.js` 的 `refreshLiveOdds()` | `index.html` 的 `bootApp()` |

**两条通道口径必须一致**，改一处必须改另一处（两个运行时无法共用模块）。已实测同一份真实数据下
两边的 `hc7`/`max7` 倍数与方案卡数字逐字符相同，且由 `node tools/_smoke_parity.js` **每次跑都重新验一遍**
（喂同一份输入给两个模块，断言输出逐字符相同；并逐个对齐 12 个同名导出函数）。
★这条防线不能省：两边各自与自己一致时**各自的冒烟都是绿的**，只改一边造成的漂移没有任何其它地方拦得住。
写这条冒烟时发现 `legNum`/`id3` 只在内部用、两边都没导出 —— 已补进导出面，导不出来的函数就是对不齐的函数。
共用的几条硬规则：

- **先渲快照再叠加**：首屏立刻出构建值，绝不为了等网络把页面拖白；取数失败就保持快照 + 顶部标注。
- **纯函数**：`overlay()/overlayDay()` 不改入参，失败时原样返回入参。
- **日期闸**：只在「日对象日期 == 北京时间今天」时叠加。补看历史某天时官方池里当然没有那些场次，
  无条件叠加会把整页历史误标成"已停售"。
- ★**选项→赔率下标必须整词匹配**：「客胜」含'胜'字，按单字判会归到主胜（下标 0），客胜腿就会
  拿到主胜的赔率。此坑由 `_smoke_live_odds.js` 的冻结赔率反算自证抓出（21/21 全中，242 条已结算腿跳过）。
- **方案倍数要跟着重算**：`plan[].pct`（卡上大号数字）与 `hc7/max7.totalOdds` 是构建脚本**同源写两处**
  的同一个数，腿实时化了它就不能停在旧字面量上（9-15 实测让球七关已从 858 漂到 705）。
  但 `totalOdds` 原文本身是**手写字面量**（73 个历史方案块里只有 39 个能被连乘重建），所以：
  多段倍数（如「胆拖…约3.5倍;7关全串约26倍」）一律不碰；有已结算腿不重算；标注落在「倍」**后面**。
  `plan[].pct` 只做**同值替换**（数字完全相等才换），不按方案名猜。
- 方案**正文**里括号中的赔率（如 `010让-1主胜(2.20`）是模型当时的推理记录，**不逐条改写** ——
  改一半会让推理文句前后不搭。两侧都在方案区顶部统一加一行口径说明，指向上方场次卡的实时价。
- ★**让球-only 场（官方只开让球、没开胜平负）的判定以官方池为准**：显示换让球口径、
  建腿强制 `jcHhad` —— 见下一节。这一条只改一侧，就会出现「一边把投不了的方向当可投、一边不当」。

### 让球-only：官方只开让球、没开胜平负（2026-09-15）

**为什么单开一条：** 9-15 用户指出「013 皇马是-2球的盘，没有开不让球的胜平负」——
竞彩有些场次**只有让球盘（hhad），压根没有胜平负（310）**。而场次卡上原来顶着一个
**胜平负口径的方向**（`客胜` + ★），那是**投不了**的东西：官方没这个盘。

**判定（`noHadOf`）：** 官方 `hhad` 池里有它、`had` 池里**没有**它。三条硬规则：

- ★**以官方池为准，不以快照为准**。构建时开着 310、临场关掉（或反过来，构建时没开、临场才开）都存在，
  只有官方池说了算 → 叠加时**显式**写 `noHad = !r.sp && !!r.hhad`，不留给快照推断。
- 拿不到官方池（历史日 / 取数失败）才退回**快照推断**：`!m.sp && m.hhad.length === 3`。
  构建脚本正是按这个形态写的，所以两条路给出的答案平时一致。
- 让球-only **≠ 已停售**：它在官方池里（在售），只是没有 310 那一列。别把两者混为一谈。

**显示口径（两侧同改）：** 徽章换「让球」（琥珀 `badge-rang` / `dtag-rang`），方向前缀让球线
（`让+2 客胜` —— 与 `cart.js` 建让球腿的 `pick` 同一串写法，同一列赔率），SP 格写
**「无胜平负 · 仅让球」**（而不是「SP未开售」：不是还没开售，是压根没有这个盘），下挂一句
`※ 官方未开胜平负(仅让+2)：「客胜」不可投; 可投的是下行让球SP`。弃选场不抢徽章（那是更强的判断）。
★盘口一律**带符号**写（`让+2`/`让-1`）：原来正号省略成 `让2`，与紧邻的方向行并排会看着像两个盘。

**建腿（`cart.buildLeg`）：** 默认腿型是 `jcHad`，不拦就会往票里塞一条 `odds: ''`、
`calc` 算成奖金 0 的**买不到的单** → `makeLeg` 里对让球-only 场强制走 `jcHhad`，
页面上的 `⇄ 胜平负/让球` 开关也换成静态的「仅让球盘」。

**方案卡正文的口径说明（`noHadNote`）：** 方案卡正文是构建时写死的一句话，可能把这类场次
**当胜平负写**（如 `双选:008阿拉维斯(主胜) / 013皇马(客胜)`）。正文**一个字都不动**，
只在卡片下方加一行算出来的提醒：「⚠ 其中 009 / 013 官方只开让球、没开胜平负, 方向仅供判断、不可投;
可投的是场次卡上的「让球SP」」。识别规则是**字符串匹配**，只看正文自己怎么引用这场：

- 命中 = 三位场次号后面**紧跟这场主队或客队名的首字**（`013皇马` / `009阿贾克斯` / `013AC米兰`）；
- 不命中 = `013让+2负`（后面是「让」，本来就是让球口径）、`013:0-2`（比分口径）、`1013`（前一位是数字）；
- ★**光有场次号不算**（`009/013双选` 这种列举式不挂）—— 场次号是**各彩种各自的编号**，
  北单卡的正文写的是北单官方编号（`003叻武里场1/0`），拿竞彩的 003 去认就会错挂一句。
- 因为是字符串匹配，认不出语义：正文写别名 / 「主队」这类泛称会**漏挂**（宁可漏，不可错挂）。
  但**挂不挂是算出来的** —— 由「今天哪几场没开 310」和正文自己决定，构建脚本不用管，卡名改版也不会失效。
- ⚠它随**实时叠加**一起算（拿得到官方池时以官方池为准）。取数失败时方案卡不挂说明，
  但场次卡上的让球口径仍在（走快照推断）—— 信息不丢，只是低一行。

并**故意漏掉首场**造出"已停售"。理由：拿快照价当实时值的话，"漂移后该等于多少"自己也得用被测代码的
算法算一遍，断言就空了；固定价可以手算（让球七关 1.5·3.5·3.5·1.5·3.5·5·5 = 2411.72 → 2412）后硬写进断言。
构建值 858 能被 2.20×3.58×3.55×2.42×3.40×1.75×2.13 = 857.5 反算出来，同一条断言顺带证明
"选项→赔率下标"没串行（让胜→主胜列 / 让负→客胜列）。

模拟器验收：`cli auto --project .../miniprogram` 后用 `node tools/_mini_verify.js`，
首页应显示当日日期、无「拉取失败」横幅。真机扫预览码后**无需打开调试**即可拉到当日数据。
